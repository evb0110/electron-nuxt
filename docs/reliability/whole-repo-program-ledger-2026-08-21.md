## Destination

Produce an evidence-backed inventory of breakages, inconsistencies, and material inefficiencies across EVB Viewer. Convert validated findings into blockers-first implementation tickets, land each safe fix through isolated worktrees, and record verification through remote `main`.

## Safety and publication rules

- Do not modify the user's original checkout or any pre-existing worktree.
- Start every implementation slice from freshly fetched `origin/main`.
- Give each worker an explicit subsystem and file ownership. Never let two agents edit one worktree.
- A suspicion becomes `validated` only with a repeatable failure, a failing regression test, or direct static proof.
- Run focused tests throughout and the applicable full gates before review.
- Run CodeRabbit CLI against `main` before committing. Use at most two passes normally and never authorize paid credits.
- After committing, run `node scripts/review-cubic-commits.mjs --commit HEAD`.
- If Cubic causes an effective diff change, amend, rerun affected gates, and rerun CodeRabbit.
- Fetch `origin/main` immediately before publication. Integrate any advance without force, rerun affected gates and review when the effective diff changes, then push `HEAD:main`.
- Verify the pushed commit is an ancestor of `origin/main` before removing the worktree and temporary branch.
- Preserve any dirty, unmerged, unreviewed, or unpushed worktree and record its recovery path instead of deleting it.

## Status vocabulary

- `candidate`: plausible problem that still needs proof
- `validated`: reproduced or proven problem
- `decision-needed`: evidence is sufficient, but the correct behavior requires a product or architecture decision
- `ready`: scoped ticket with acceptance criteria and no unresolved blockers
- `in-progress`: claimed in an isolated implementation worktree
- `verified`: implementation and required local review are complete
- `done`: pushed commit is verified on remote `main` and the task worktree is cleaned up
- `blocked`: an external dependency or unresolved decision prevents progress
- `rejected`: evidence disproved the candidate or the proposed change would be unsound
- `duplicate`: another ledger item owns the same underlying problem

## Decisions

- D-001: `/privacy` remains indexable and must appear in the sitemap because the app already prerenders it and publishes a canonical URL.
- D-002: typed aborts are the only ignored cancellation class. Unknown unhandled rejections enter coordinated fatal shutdown with recovery preservation.
- D-003: release activation is an idempotent reconciliation process with bounded retry and partial-state alerts. It is not described as atomic.
- D-004: desktop recovery owns one journal per window and restores all prior windows. Transfer targets start empty, and live owners cannot be claimed.
- D-005: versioned IndexedDB state owns browser Recent Files and durable-record retention. LocalStorage is not a deletion authority.
